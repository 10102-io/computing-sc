## What wave A changes, and why

### TransferEOALegacy, the clone implementation (new legacies only)

`contracts/forwarding/TransferLegacyEOAContract.sol`. A new implementation
for new creates; every existing clone keeps the implementation and vault it
pinned at creation.

- **M-2** (checklist audit): `_transferErc20ToBeneficiary`'s direct rail was
  `try IERC20.transferFrom` with a bool return. USDT returns nothing, the
  decode fails outside the `try`, and the whole claim (and its fee pull)
  reverts. It is now `SafeERC20.trySafeTransferFrom` (OZ 5.6.1): no-return
  tokens pay out, a `false` return or a revert counts as a failed transfer
  (0, never a claim-wide revert). Spec: the old rail reverting on
  `MockNoReturnERC20`, a direct USDT allowance claimed with its fee, and a
  token that returns `false` skipped while the rest of the batch pays.
- **M-4**: `activeLegacyAndUnswap` reverts `ZeroAmountOutMin` when a
  non-WETH storage token is actually swapped with `amountOutMin_ == 0`;
  WETH unwraps 1:1 and needs none; nothing pullable needs none. The owner's
  `unswap` has the same rule.
- **eoa-unswap-weth**: the owner's `unswap` of a WETH storage token
  unwraps through `IWETH.withdraw` and pays ETH (the Uniswap path
  `[WETH, WETH]` reverted with `IDENTICAL_ADDRESSES`), honouring the deadline.
- **legacy-claim-fee-cap**: `initialize` refuses a claim fee above
  `MAX_ADMIN_FEE_BPS = 50` (`AdminFeeAboveCap`), whoever set it on `Payment`.
- Extension hooks for wave B (`_activationDeadline`,
  `_afterBeneficiariesChanged`, `_route`, internal visibility). Behaviour is
  unchanged (the whole suite runs on them); bytecode moved by a few bytes.
- **Etherscan verification** (DEFERRED "Etherscan verification of mainnet
  `TransferEOALegacy` clone target"): the April 2026 target could not be
  verified because its bytecode could not be reproduced from the committed
  input (a viaIR input-order issue under solc 0.8.20). The new clone
  implementations compile in **their own Hardhat job** (a per-file
  `overrides` entry in `hardhat.config.ts`), so the build-info input is
  exactly the file's dependency closure, which is what verification
  submits. `scripts/check-clone-reproducible.ts` recompiles that minimal
  input with the cached native solc: **byte-identical for both clones**.
  viaIR stays on (without it the clone is "stack too deep"); solc 0.8.35
  (the repo's compiler since 2026-07-23) also produced identical bytecode
  in a repo-wide input, so the April issue does not reproduce on it.

What `_swapAdminFee` keeps, by decision: it swaps the fee with
`amountOutMin = 0`. It moves only the fee (25 bps today, at most 50), and a
failed swap already falls back to sending the token itself. A sandwich can
take part of the fee, never user funds. **Recommendation** for a later
implementation: swap only above a dust threshold and with a minimum from a
TWAP or a router quote minus 3%, or stop swapping and let `Payment` hold
the token (the treasury converts in batches). Not done here: it changes
nothing for users and would add an oracle dependency to every claim.

### LegacyPullVaultV2 (new deployment)

`contracts/common/LegacyPullVaultV2.sol`. LegacyPullVault (v1,
`0x95F0…f978`) is unchanged and keeps serving every legacy bound to it.

- **M-1**: `unbind()` lets the owner clear a binding to a legacy that is no
  longer live. An activated legacy stays bound because multi-tranche claims
  keep pulling through it, so its beneficiaries could lift the owner's next
  permit from the mempool, register it in Permit2 first and pull the new
  allowances through the old legacy. A live binding cannot be cleared this
  way, so a phished owner cannot silently break their own inheritance.
  Spec: the front-run steals the wallet on v1 and pulls nothing on v2
  after `unbind`.
- **Several clone implementations**: the codehash allowlist starts with the
  constructor's implementation; only the UpgradeTimelock (an immutable) can
  add one (`allowImplementation`), never remove one. See "Vault design
  across waves".
- **NFT rails** for wave B: `pullERC721` / `pullERC1155`, bound legacy
  only. Wave A clones never call them.

Unchanged guarantees: `bind` is router-only, checks the codehash and the
owner, replaces only a non-live binding; `pull` and `release` answer only
to the bound legacy; no upgrade, nothing an admin can do to a binding or to
funds.

### TransferEOALegacyRouter (implementation upgrade)

`contracts/forwarding/TransferLegacyEOAContractRouter.sol`.

- **M-3**: `setLegacyImplementation`, `setPullVault`, `setActivityAttestor`
  and `setLegacyCreationCode` answer only to the UpgradeTimelock; each
  emits an event (`LegacyImplementationSet`, `LegacyCreationCodeSet` are
  new; `PullVaultSet`, `ActivityAttestorSet` unchanged). `setCreatePaused`
  stays on the code admin.
- **How the timelock reaches the implementation**: an `immutable
  upgradeTimelock` set in the implementation's constructor. It costs no
  storage slot (layout untouched), it cannot change except by an
  implementation swap, which itself needs the timelock, so the gate's trust
  root is the upgrade path's; the price is one constructor argument per
  network (`deploy-impl.ts` reads it from `contract-addresses.json`).
  Storage would have needed a setter or a reinitializer, i.e. a second
  lever to protect.
- **initializeV4** (`reinitializer(5)`, callable **only by the
  UpgradeTimelock**): moves the code admin (now just the pause) to the
  governance Safe, and repoints `paymentContract` when given one (Sepolia
  still points at the orphan `0x7D78…ae8E`; 0 leaves mainnet's unchanged).
  It runs as a separate item right after the upgrade in the same batch, not
  through `upgradeAndCall`: the proxy's admin would be `msg.sender` there,
  and a reinitializer anyone could call before the batch would be a
  front-run. Live counters, read 2026-11-04: mainnet 4, Sepolia 3; both
  reach 5.
- **legacy-claim-fee-cap**: `createLegacyV2WithMaxFee(…, maxFeeBps)`
  reverts `FeeAboveMax` when the snapshotted fee exceeds what the creator
  was shown. `createLegacyV2` and the v1 `createLegacy` are unchanged.
- **auto-renew-nonce-baseline**: the monotonic nonce bound is per attestor
  (`attestorNonceSeen[legacyId][attestor]`, appended at slot 17). A
  compromised attestor citing `type(uint64).max` locks out only itself, and
  rotating the attestor restores renewals. `autoRenewState.lastNonceSeen` is
  still written (the latest observation) but no longer gates anything.
  Migration: exact on mainnet (no legacy has opted in); on Sepolia the
  current attestor could re-cite one old observation once (delay only).
- **router-create-hardening** (EOA side): `autoSwap` into a non-WETH token
  with a zero minimum reverts, for every legacy (router-level). The app
  always quotes a minimum.

Size: 23,844 of 24,576 bytes. The fee-bounded create costs 3 KiB (its
calldata decoding); the next router change will need room, and the
candidate is the v1 `createLegacy` shim, which the app's `createWill` still
calls.

### TimeLockRouter (implementation upgrade)

- **router-create-hardening**: every create path reverts `EmptyTimelock`
  when nothing is locked (ETH attached to an empty create stayed in the
  router), and an ETH swap into a non-WETH token with `amountOutMin == 0`
  reverts `ZeroAmountOutMin`.
- **autopilot-unlock-at**: `createTimelockUntil(TimelockRegular, uint64
  unlockAt)`. The lock opens at `unlockAt` exactly, whenever the transaction
  lands; the struct's `duration` must be 0 so the date has one source.

### PremiumRegistry (implementation upgrade)

**premium-coupons** and **referral-onchain** in one upgrade.

- Coupons: `setCoupon(code, discountBps, expiresAt, maxUses, referrer,
  active)` (OPERATOR; discount capped at 50%; keyed by `keccak256(code)`,
  uses kept on update). `couponDiscountBps(code)` for the pricing page.
- Referrers: `setReferrer(referrer, shareBps)` (DEFAULT_ADMIN, i.e. the Safe
  or the deployer; capped at 30%). The share goes straight from the buyer to
  the referrer; the registry never holds funds. A referrer the token
  refuses (blocklisted) or whose ETH receive reverts forfeits the share to
  `Payment`, and the purchase still lands. Self-referral is attributed,
  never paid. A coupon's referrer wins over the referrer argument.
- New entry points `subscribeWithUSDT/USDC/ETH(plan, code, referrer)`
  (correct spelling; the `subcribeWith*` v1 functions are unchanged, so
  ethers v5 callers are not broken by overloads). A set code that is not
  usable reverts instead of charging full price.
- Events: the unchanged `PlanSubcribed` (the worker's ledger reads it) plus
  `PlanSubscribedWithCode(user, plan, method, value, code, referrer,
  referrerShare)`, `CouponSet`, `ReferrerSet`. On-chain attribution is the
  purchase event itself, so referral-onchain's separate attribution
  registry is not needed.

Codes travel in clear calldata: once used, a code is public. Cap scarce
codes with `maxUses` and `expiresAt`.

### PremiumSetting (implementation upgrade)

Founder decision on DEFERRED "Multisig legacy creator-only off-chain admin":
a multisig legacy's own Safe (its recorded owner, matching the router's
`onlySafeWallet`) may call `setWatchers`, `clearWatcher`,
`updateLegacyConfig`, `clearLegacyConfig` and `clearLegacyPII`, next to the
creator. No per-owner scope. Premium and reminder timing stay the
creator's, and events keep `user = creator`, so the subgraph and the worker
see the same keys either way. `setReminderConfigs` still sets the caller's
own timing. EOA legacies are unaffected (owner == creator).

### EIP712LegacyVerifier (implementation upgrade)

`recordSelfConsent(termsHash, refContract, refId)` records "msg.sender
accepted the active terms for (contract, id)" in an append-only per-user log
(`getUserSelfConsent*`) with a `SelfConsentRecorded` event. `termsHash` must
be the active one, so a terms change between display and transaction
reverts. This closes **shield-vault-consent** without a ShieldVault v3:
the app records consent in the user's own transaction next to `open`, and
nothing calls into or out of the immutable vault.

## Vault design across waves

LegacyPullVaultV2 deploys in wave A and must also serve the v3 clone. Two
options:

1. Pin both codehashes at construction: v3's implementation address would
   have to be final before wave A deploys, i.e. before its independent
   audit, and any audit fix changes the address. Rejected.
2. **Chosen:** a timelock-only, add-only codehash allowlist. The trust it
   adds is nil: the timelock can already swap the router, which decides
   what gets bound, and the router's `setLegacyImplementation` is
   timelocked from this train on. Add-only means no operation can ever
   strand a legacy that bound under an allowed implementation. The
   allowlist is per vault, the timelock address is immutable, and an
   allowed codehash that the router no longer creates is unreachable (bind
   is router-only). Spec: only the timelock adds, no removal, unknown
   codehash fails the create, clones of both implementations bind and pull.

## Wave B: legacy v3 (after the independent audit)

### What it is

`contracts/forwarding/TransferLegacyEOAContractV3.sol` (`TransferEOALegacyV3
is TransferEOALegacy`), `contracts/whitelist/NftCollectionWhiteList.sol`,
`test/Train2026-11.v3.spec.ts`. No router change: the new settings are
called on the legacy by its owner directly, and check-ins and fungible
claims keep going through the router. Every feature is off by default; a v3
legacy with nothing set behaves exactly like a wave A legacy.

1. **NFTs on an allowlist.** The owner names ERC-721 / ERC-1155 items
   (`setNftItems`, at most 50), each from a collection on the
   NftCollectionWhiteList and assigned to a first-line beneficiary. The
   list is checked when items are named, **never at claim**, so a later
   delisting cannot stop an heir. Items stay in the owner's wallet;
   `claimNfts(indexes)` moves them through LegacyPullVaultV2 (the owner
   approves that one verified operator) or a direct approval to the
   legacy. First line: any first-line beneficiary triggers, each item goes
   to its named beneficiary. Second or third line in its period: every item
   to the claimant. ERC-1155 moves up to the named amount. Failures are
   skipped, never revert the batch. No claim fee on NFTs.
   **Administration:** like TokenWhiteList, the deployer key at deployment
   and the governance Safe added as co-admin (`scripts/add-safe-admin.ts`).
   The list address is an immutable of the v3 implementation; changing it
   is a new implementation (timelocked through `setLegacyImplementation`).
2. **Per-beneficiary backup lines** (premium, optional). `setBackupLines(
   backupDelay, lines)` turns per-share mode on: each first-line share is
   claimed by its own line, A from the activation deadline, A2 from
   `backupDelay` later (30 days to 10 years), A3 from twice that. The first
   to claim a token's share takes it, a new inflow after every share was
   paid opens a new round, and the whole-estate second and third lines work
   as before. Backups can never be the owner, a beneficiary, the executor
   or on two lines. Any first-line change voids the lines (per-share off)
   and the NFT items.
3. **An executor** (optional). `setExecutor(addr)`; it can never be the
   owner, a beneficiary or a backup, and the contract rejects any later
   change that would make it one. `attestDeath()` brings the activation
   deadline forward to `DEATH_GRACE` (30 days) after the attestation; any
   owner activity in between (a check-in, any owner action, an auto-renew
   on observed activity) cancels it; at most one attestation per grace
   period. The dead-owner test holds: claims open at the normal deadline
   without it, and it never holds or receives anything.

Size: 24,334 of 24,576 bytes, compiled for size (`runs: 1` in its own job).
An audit fix that adds code needs trimming first; candidates are the
`claimedMask` / `primaryOf` views and the ERC-1155 partial-balance path.

### Hardhat 3 and ethers 6: why not now

The condition was byte-identical artifacts for every deployed contract and
a green suite. Probe (Hardhat 3.21.2 in a scratch folder, LegacyPullVault
v1, same solc 0.8.35 and settings): the executable code is identical, but
Hardhat 3 compiles project files under the source unit name
`project/contracts/…`, which changes the metadata hash, so **the full
deployed bytecode differs for every contract**. The artifacts would no
longer reproduce what is on chain byte for byte. Beyond that, the only
`hardhat-deploy` line for Hardhat 3 (2.x) is a rewrite on `rocketh`: every
deploy script, `deployments.get` in `timelock-op.ts` and the other
scripts, and the `deployments/` artifact store would change, and all 30
spec files are written against ethers v5 (`BigNumber`, `ethers.utils`,
`_signTypedData`). Nothing was changed for it. Revisit as its own round
with no train queued, and decide first whether reproducing deployed
bytecode from this repo matters more than the toolchain's dev-only
advisories.
