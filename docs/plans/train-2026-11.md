## What wave A changes, and why

### TransferEOALegacy, the clone implementation (new legacies only)

`contracts/forwarding/TransferLegacyEOAContract.sol`. A new implementation
for new creates; every existing clone keeps the implementation and vault it
pinned at creation. **Deploy it from the branch HEAD** (A2): earlier
commits, such as the pre-rebase `8d63783` a reviewer read, still had
`setDelayLayer23`.

- **M-2** (checklist audit): `_transferErc20ToBeneficiary`'s direct rail was
  `try IERC20.transferFrom` with a bool return. USDT returns nothing, the
  decode fails outside the `try`, and the whole claim (and its fee pull)
  reverts. It is now `SafeERC20.trySafeTransferFrom` (OZ 5.6.1): no-return
  tokens pay out, a `false` return or a revert counts as a failed transfer
  (0, never a claim-wide revert).
- **M-4**: `activeLegacyAndUnswap` reverts `ZeroAmountOutMin` when a
  non-WETH storage token is actually swapped with `amountOutMin_ == 0`; WETH
  unwraps 1:1 and needs none. The owner's `unswap` has the same rule.
- **Review L-3** (the other half of M-4): a co-beneficiary could still pass a
  token minimum of 1 and sandwich the swap of everyone's share while bearing
  only their part of the loss. The non-WETH unswap claim now requires the
  caller to be the sole recipient of their layer (`UnswapNeedsSoleRecipient`);
  co-recipients claim the token itself with `activeLegacy`.
- **eoa-unswap-weth**: the owner's `unswap` of a WETH storage token
  unwraps through `IWETH.withdraw` and pays ETH, honouring the deadline.
  `unswap` clears the storage token and records owner activity before any
  external call (review round 2).
- **legacy-claim-fee-cap**: `initialize` refuses a claim fee above
  `MAX_ADMIN_FEE_BPS = 50` (`AdminFeeAboveCap`), whoever set it on `Payment`.
- **Owner ETH by checked call**: `withdraw` and `deleteLegacy` pay the owner
  with a checked `call` instead of `transfer`, whose 2,300 gas breaks an owner
  that is a contract or an EIP-7702 account. Only the owner is paid, after
  every state change; `deleteLegacy` sends nothing when there is nothing.
- Dead code removed: `setDelayLayer23` (router-only, never called by any
  router). The ETH-branch `require` string is a custom error.
- Extension hooks for wave B (`_activationDeadline`,
  `_afterBeneficiariesChanged`, `_checkUnswapClaim`, `_route`, internal
  visibility). Behaviour is unchanged; the whole suite runs on them.
- **Etherscan verification** (DEFERRED "Etherscan verification of mainnet
  `TransferEOALegacy` clone target"): the April 2026 target could not be
  verified because its bytecode could not be reproduced from the committed
  input (a viaIR input-order issue under solc 0.8.20). Both clone
  implementations compile in **their own Hardhat job** (per-file
  `overrides`, same settings as the repo), so the build-info input is exactly
  the file's dependency closure, which is what verification submits.
  `scripts/check-clone-reproducible.ts` recompiles that input with the cached
  native solc: **byte-identical for both clones**.
  Update 2026-11-12: the old targets are reproduced after all. The April
  target `0x314F…233C` equals the build of the recorded input `edea9ede…`
  as a whole, and the May target `0xD5bA…2200` the incremental job Hardhat
  ran after one file changed. It was the set of files in the compile job,
  not their order (`docs/security/compiler-known-bugs.md` section 2.3).
  Both are verified on Sourcify (exact match) and Etherscan since that day,
  with the 22 first EOA legacies.

What `_swapAdminFee` keeps on the deployed clone, by decision: it swaps
the fee with `amountOutMin = 0`. It moves only the fee (25 bps today, at
most 50), and a failed swap already falls back to sending the token itself.
A sandwich can take part of the fee, never user funds. The next clone (v3
and the base it inherits, round 10) stops swapping: `Payment` receives the
token itself.

### LegacyPullVaultV2 (new deployment)

`contracts/common/LegacyPullVaultV2.sol`. LegacyPullVault (v1,
`0x95F0…f978`) is unchanged and keeps serving every legacy bound to it.

- **M-1**: `unbind()` lets the owner clear a binding to a legacy that is no
  longer live, before signing anything for a new legacy. A live binding
  cannot be cleared this way, so a phished owner cannot silently break their
  own inheritance.
- **Several clone implementations**: the codehash allowlist starts with the
  constructor's implementation; only the UpgradeTimelock can add one, never
  remove one (see "Vault design across waves").
- **NFT rails** for wave B: `pullERC721` / `pullERC1155`, bound legacy only.

Unchanged guarantees: `bind` is router-only, checks the codehash and the
owner, replaces only a non-live binding; `pull` and `release` answer only to
the bound legacy; no upgrade, nothing an admin can do to a binding or funds.

### TransferEOALegacyRouter (implementation upgrade)

- **M-3**: `setLegacyImplementation`, `setPullVault`, `setLegacyCreationCode`
  and installing an attestor answer only to the UpgradeTimelock, each with an
  event. `setCreatePaused` stays on the code admin.
- **Attestor kill switch** (founder decision 2026-11-04): the code admin
  may set the attestor to address(0) at once; any non-zero attestor still
  needs the timelock. Removal can only stop renewals, which fails safe.
- **How the timelock reaches the implementation**: an `immutable
  upgradeTimelock` set in the implementation's constructor. No storage slot;
  it changes only with an implementation swap, which itself needs the
  timelock, so the gate's trust root is the upgrade path's.
- **initializeV4** (`reinitializer(5)`, callable **only by the
  UpgradeTimelock**): moves the code admin (the pause and the kill switch)
  to the governance Safe and repoints `paymentContract` when given one
  (Sepolia's orphan `0x7D78…ae8E`). It runs as the item right after the
  upgrade in the same batch; `upgradeAndCall` would make the proxy admin the
  caller, and an ungated reinitializer could be front-run. Live counters,
  read 2026-11-04: mainnet 4, Sepolia 3; both reach 5. **It runs once**: any
  later batch that re-upgrades the router must not repeat it (the whole
  batch would revert; rehearsed).
- **initializeV2 / initializeV3 removed** (review): they set the code admin
  with no caller check and are unreachable once the counter is 5. A fresh
  deployment goes `initialize`, then `initializeV4` from the timelock (on a
  local chain the deployer stands in for it).
- **legacy-claim-fee-cap**: `createLegacyV2WithMaxFee(…, maxFeeBps)` reverts
  `FeeAboveMax` when the snapshotted fee exceeds what the creator was shown.
- **auto-renew-nonce-baseline**: the monotonic nonce bound is per attestor
  (`attestorNonceSeen`, appended at slot 17). `autoRenewState.lastNonceSeen`
  is still written but gates nothing (comments corrected in review).
- **router-create-hardening** (EOA side): `autoSwap` into a non-WETH token
  with a zero minimum reverts, for every legacy.
- **Unswap claim guard for existing clones** (review round 2): when a
  legacy's `eoaStorageToken()` is set and is not WETH, the router's
  `activeLegacyAndUnswap` requires a nonzero minimum (`ZeroAmountOutMin`)
  and the caller to be the sole recipient of their layer
  (`getBeneficiaries(caller).length == 1`, else `UnswapNeedsSoleRecipient`).
  Old clones have neither guard. Every clone vintage on mainnet (the five
  implementations `0xdDea11D9`, `0x314F512C`, `0xD5bA2799`, `0x19E46cf9`,
  `0x148469d1` and the 22 pre-clone full contracts) exposes both reads
  (legacy 1 has no unswap claim at all). Exposure today: 0 of 44 legacies;
  this covers the window before the train and old-clone owners who add
  co-beneficiaries later. Spec: the live mainnet clone code behind the new
  router (`Train2026-11.oldclones.spec.ts`).
- **v1 `createLegacy`** (founder decision): stays in this train; it is
  dropped in the next router change, after the app removes its `createWill`
  fallback. Router headroom is now 1,536 bytes.

### TimeLockRouter (implementation upgrade)

- **router-create-hardening**: every create path reverts `EmptyTimelock`
  when nothing is locked, and an ETH swap into a non-WETH token with
  `amountOutMin == 0` reverts `ZeroAmountOutMin`.
- **autopilot-unlock-at**: `createTimelockUntil(TimelockRegular, uint64
  unlockAt)`; the lock opens at `unlockAt` exactly; `duration` must be 0.
- **Review L-2**: the implementation's constructor calls
  `_disableInitializers()` (no storage).

### PremiumRegistry (implementation upgrade)

**premium-coupons** and **referral-onchain** in one upgrade: operator-set
coupons (`setCoupon`, at most 50%, expiry, use cap), admin-registered
referrer shares (`setReferrer`, at most 30%) paid straight from the buyer,
through new `subscribeWithUSDT/USDC/ETH(plan, code, referrer)` entry points.
`PlanSubcribed` keeps emitting (its `value` is the total paid, **including
the referrer's share**) next to the new `PlanSubscribedWithCode` (with
`referrerShare`). A referrer the token refuses or whose ETH receive reverts
forfeits the share to `Payment`; self-referral is attributed, never paid;
codes travel in clear calldata. Caps confirmed by the founder.

### PremiumSetting (implementation upgrade)

- A multisig legacy's own Safe may call `setWatchers`, `clearWatcher`,
  `updateLegacyConfig`, `clearLegacyConfig`, `clearLegacyPII` next to the
  creator (founder decision); premium, timing and the events' `user` stay
  the creator's.
- **Review L-1**: any contract could pose as a legacy, answer with another
  legacy's id and type and a premium creator, and forge notification events
  for it (pre-existing). Every setter now first proves the legacy is real:
  the router for its type must return it from `legacyAddresses(id)`
  (`NotALegacy` otherwise).

### EIP712LegacyVerifier (implementation upgrade)

`recordSelfConsent(termsHash, refContract, refId)`: an append-only per-user
record that the caller accepted the active terms for a reference such as a
ShieldVault position, with `SelfConsentRecorded`. Closes
**shield-vault-consent** without a ShieldVault v3.

## What existing users keep

Existing EOA clones pin their implementation and vault forever. Until they
delete and recreate, they keep:

| Behaviour | Old clones | What the app already does |
|---|---|---|
| Direct USDT allowance reverts the whole claim (M-2) | yes | routes USDT through Permit2 only (no live legacy has a direct USDT allowance) |
| Zero-minimum or co-recipient unswap claim (M-4, L-3) | no longer: the new router refuses both for every clone (review round 2) | quotes the router and accepts at most 2% less; co-beneficiaries must be routed to the token claim (follow-up) |
| Owner `unswap` of WETH reverts | yes | never calls `unswap`; WETH is unwrapped in the owner's wallet |
| No 50 bps fee cap | yes | the admin panel refuses more than 0.5%; `Payment` is Safe-only |
| `transfer` to the owner on withdraw and delete | yes | EOA owners are unaffected |
| Activated legacy stays bound in vault v1 (M-1) | yes, v1 has no `unbind` | creates with an empty bundle first when `boundLegacy(owner)` is not live, then sets allowances |

Router-level changes apply to every legacy: the timelocked levers, the Safe
as pauser and kill switch, the per-attestor baseline, the zero-minimum
`autoSwap` refusal, and the unswap claim guard.

## Vault design across waves

LegacyPullVaultV2 deploys in wave A and must also serve v3. Pinning both
codehashes at construction would need v3's final address before its audit.
**Chosen:** a timelock-only, add-only codehash allowlist. It adds no trust:
the timelock already swaps the router, which decides what gets bound, and
`setLegacyImplementation` is timelocked from this train on. Add-only means
nothing can strand a legacy that bound under an allowed implementation; an
allowed codehash the router no longer creates is unreachable (bind is
router-only).

## Wave B: legacy v3 (after the independent audit)

### What it is

`contracts/forwarding/TransferLegacyEOAContractV3.sol` (`TransferEOALegacyV3
is TransferEOALegacy`), `contracts/whitelist/NftCollectionWhiteList.sol`,
`test/Train2026-11.v3.spec.ts`. The v3 settings are called on the legacy by
its owner directly; check-ins and token claims still go through the router.
Every feature is off by default. Round 10 adds items 4 and 5 below: one
change to the clone code v3 inherits and one router implementation upgrade
(no new router function, storage unchanged).

1. **NFTs on an allowlist** (open to every owner). `setNftItems` (at most
   50): each item names a collection, its kind (1 = ERC-721 with amount 1,
   2 = ERC-1155), which must match the NftCollectionWhiteList when named, and
   a first-line beneficiary. The list is never read at claim, so a delisting
   cannot stop an heir; the recorded kind drives the claim. `claimNfts`
   moves items through LegacyPullVaultV2 (the owner approves that one
   operator) or a direct approval. First line: the item's named beneficiary
   (any first-line claimant triggers); per-share mode: whoever of that
   beneficiary's line claims in their window; second or third line in its
   period: every item to the claimant, in per-share mode only the items of
   shares whose own line never claimed. An ERC-1155 item moves in parts and
   the remainder stays owed. The legacy activates only when something moves,
   and then emits `LegacyActivated(legacyId, layer, timestamp)`. No claim fee
   on NFTs. **Administration:** the deployer key at deployment, the Safe as
   co-admin (`add-safe-admin.ts`), like TokenWhiteList (same license,
   `UNLICENSED`). The list address is an immutable of the v3 implementation.
2. **Per-beneficiary backup lines** (Premium). `setBackupLines(backupDelay,
   lines)` turns per-share mode on. Each first-line share is a running
   account per token: a claim pays the share's percentage of everything the
   token ever made available to the first line, minus what the share already
   received (`totalReleased`, `released`). Claim order and inflows between
   claims take nothing from anyone, and no heir waits for another. A share is
   claimed by its line: A from the deadline, A2 from `backupDelay` later
   (30 days to 10 years), A3 from twice that. **A share belongs to the
   first address that receives anything from it** (tokens, ETH or an NFT
   unit), on whatever line (`shareOwner`, round 7); from then on only that
   address receives from it, later inflows, other tokens and its NFTs
   included. A first-line member claims a share only while nobody else owns
   it (`ShareOwned`); a second- or third-line claim in its period takes only
   the shares nobody else owns and owns each one it is paid from (founder
   decision, round 3, sharpened in round 7). Ownership is recorded only where
   value moved, so an empty or failed claim owns nothing. Without backup
   lines the whole-estate fallback is unchanged. The unswap claim
   is refused in per-share mode (heirs claim the token or ETH). Backups can
   never be the owner, a beneficiary on any line, the executor, or on two
   lines, now or later, and backups must open before the second line
   (`delayLayer2 >= 2 × backupDelay`). In per-share mode no first-line
   primary is the second- or third-line beneficiary, and the first line sums
   to 100% over its distinct addresses (`FirstLineInvalid`; round 7, scoped in
   round 8): `setBackupLines` checks both when it enters or changes the
   mode, and a layer edit while the mode is on checks the overlap. Whole-estate
   mode accepts what wave A accepts (nothing strands there), and the second
   and third lines may be one address. Any first-line change voids the lines
   and the NFT items **explicitly**: it emits `BackupLinesSet(epoch, 0)` and
   `NftItemsSet(epoch, 0)`, and the app must tell the owner to set them again.
3. **An executor** (Premium). `setExecutor(addr)`; never the owner, a
   beneficiary or a backup, now or later. `attestDeath()` counts only after
   the owner has been silent for half the activation trigger; it brings the
   deadline forward to `DEATH_GRACE` (30 days) after the attestation; any
   owner activity cancels it; at most one per grace period. The dead-owner
   test holds: claims open at the normal deadline without it, and it never
   holds or receives anything. **Deploy preconditions:** the worker's owner
   alert email on `DeathAttested` must be live before wave B executes (the
   grace period is only a protection if the owner hears about it), and the
   auto-renew attestor must ignore owner activity from before an
   attestation (follow-up table, "Wave B: executor").
4. **The claim fee without a swap** (round 10, for v3 and the next base
   clone; the deployed wave A clone keeps its swap). An ERC-20 fee goes
   from the owner's wallet straight to `Payment` as the token itself, on the
   rail the payout uses (direct allowance, Permit2 with the clone as
   spender, or the vault), never through the legacy and never swapped; an
   ETH fee stays ETH. A fee transfer that fails (a token that reverts or
   blocklists `Payment`, a `Payment` that refuses ETH) never reverts the
   claim: the heirs' payout stands and the fee is **not collected and not
   owed**. It stays where it was, in the owner's wallet (the legacy, for
   ETH), as part of the estate: a later whole-estate claim distributes it,
   and in per-share mode the running totals hand it to the shares (it is
   still counted as released, K-13). `Payment` holds the tokens; the Safe
   withdraws them with `withdrawERC20` (WITHDRAWER role). `_swapAdminFee`
   and its Uniswap approval are gone; `uniswapRouter` stays for the
   owner's `unswap` and the unswap claim. `InvalidPaymentContract` stays in
   the ABI because deployed clones still revert with it.
5. **Router: the unswap guard only when something would convert** (round
   10). Wave A's router refuses `activeLegacyAndUnswap` for a non-WETH
   storage token unless the minimum is nonzero and the caller is the sole
   recipient of their layer, even when the clone would convert nothing.
   The new router implementation applies the guard only when
   `min(owner's balance, owner's direct allowance to the clone)` of the
   storage token is not zero: the pull rule of every clone version that
   has the unswap claim (unchanged since it was added on 2026-02-26), and
   the condition under which the clone itself swaps. Checked read-only on
   mainnet on 2026-11-09: 44 EOA legacies; legacy 1 (full bytecode) has no
   unswap claim and no `eoaStorageToken()` (the router call reverts there,
   before and after); the other 43 (21 full-bytecode legacies and 22
   clones of `0x314F512C`, `0xD5bA2799`, `0x19E46cf9`, `0x148469d1`,
   `0xdDea11D9`) all expose both reads; no clone of the wave A
   implementation yet. Storage layout unchanged (19 variables, identical
   to the deployed implementation on both networks).

Size: 23,490 of 24,576 bytes at 200 runs after round 11 (1,086 spare;
23,517 after round 10, where removing the fee swap freed 953). 24,470 after round 8 (106 spare; 24,423
after round 7). Round 8 made the four constants internal (no getters) to pay

### Hardhat 3 and ethers 6: why not now

Probe (Hardhat 3.21.2, LegacyPullVault v1, same solc and settings): the
executable code is identical, but Hardhat 3 compiles project files under the
source unit name `project/contracts/…`, which changes the metadata hash, so
the full deployed bytecode differs for every contract and the repo would no
longer reproduce what is on chain. The only `hardhat-deploy` line for
Hardhat 3 (2.x) is a rewrite on `rocketh` (every deploy script,
`deployments.get` in the scripts, the `deployments/` store), and every spec
is written against ethers v5. Nothing was changed for it. Revisit as its own
round with no train queued.
